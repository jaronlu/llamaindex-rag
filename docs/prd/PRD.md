# 基于 LlamaIndex 的可逐步验证知识库 PRD

## 1. 背景与目标

使用开源库 `llama_index` 构建一个基于文档的知识库，将 PDF 内容转换为可检索、可追溯的知识，并逐步支持基于资料的回答。项目同时用于系统练习 LlamaIndex、理解 RAG 技术取舍：优先使用和研究库提供的能力，在有实际需求时再编写自定义扩展。`docs/pdf/HowToLiveBetter.pdf` 是首个测试文档，目前共 458 页；后续会不定期添加其他文档，不能将该文件或其内容写死在系统中。

本项目的核心要求是将 RAG 流程拆成独立模块：每完成一个模块，即可使用该 PDF 运行测试，由人直接阅读结果并判断质量，无须等待整个系统完成。系统应展示必要的中间结果和来源，帮助定位问题，而非只给出最终答案。检索结果必须能够溯源到原始文档及具体页面，供人直接核对。

## 2. 使用者与使用场景

- 使用者：需要阅读、检索和检查文档内容的人，以及希望通过项目学习 LlamaIndex 的开发者。
- 典型场景：加载 PDF，检查指定页面的文本；查看切片是否完整；输入问题并检查召回片段；比较重排前后结果；阅读带来源的回答并回到原文核对。
- 首期交互以易读的命令行输出或本地可查看的文本结果为准；具体界面不做强制要求。输出应支持中文，避免依赖阅读原始对象、向量或代码才能理解结果。
- 进阶场景：在局域网的 iPhone 上输入问题，由本机接口完成检索与生成，并逐条核对来源。

## 3. 范围与原则

### 本期范围

- 使用 `llama_index` 及其必要的集成组件实现文档加载、切片、索引与检索、重排和基于检索结果的回答。
- 以 `docs/pdf/HowToLiveBetter.pdf` 为贯穿各阶段的首个测试样例，支持对少量指定页面或片段先做检查，再处理完整文档；支持后续添加其他文档并纳入知识库。
- 遵循开闭原则：文档加载和解析、切片、索引、检索、重排及模型等能力通过清晰的接口或配置扩展；新增文档格式或替换组件时，优先增加对应实现，无需修改既有核心流程。
- 展示各阶段输入、可读结果、来源和必要的运行信息；支持独立运行或复用前一阶段产物。
- 在现有检索、重排和回答之上提供局域网 HTTP 接口，并配套一个 iPhone 客户端；客户端不含索引、嵌入模型或云端密钥，只通过局域网调用本机接口。
- 建立可重复的测试问题和人工核验记录，比较各阶段的质量。
- 围绕各模块实践 LlamaIndex 核心概念和可选能力，记录原理、配置、实验结果与学习复盘。

### 暂不要求

- 多用户、账号体系、权限管理、生产部署及上架发布；iPhone 客户端仅用于局域网自用，不做多平台前端。
- 承诺覆盖扫描件 OCR、表格或图片的高保真解析；若测试中发现这些内容影响结果，应记录为限制和后续需求。
- 首期不要求一次支持所有文档格式；新增格式通过加载器扩展，具体格式及优先级按后续实际文档确定。
- 指定唯一模型、向量数据库或云服务。嵌入、重排和生成模型的选择应可配置；实际成本、资源要求及数据是否发送至外部服务须在使用前明确。

## 4. 流程与模块依赖

```text
PDF → 文档加载 → 文本切片 → 向量化与索引 → 检索 → 重排 → 基于来源生成回答
                         └──────── 人工检查、测试记录与问题定位 ────────┘
```

模块按上述顺序交付。后续模块可以依赖前序模块的输出，但每个模块都应提供独立测试入口，允许从已有产物或指定测试输入运行；测试方式和输出位置应随实现记录。完整文档处理耗时或成本较高时，先用固定页面范围验证，再运行全量测试。

## 5. 文档扩展与溯源要求

- 首期至少支持添加多个 PDF 文件；文件路径、文档标识和处理范围由输入或配置提供，不依赖特定文件名、页数、内容或固定测试问题。
- 每份文档须有稳定且可区分的来源标识，并保留文件名及可访问的来源位置；片段和索引记录继承其来源。不同文档即使文件名相同，也不得混淆。来源位置发生变化时应明确提示或更新映射，不能静默指向错误文件。
- 新增文档可单独加载、切片并加入知识库；已有索引与新文档索引之间的关联和更新方式须明确，避免重复添加或覆盖其他文档。实现可根据所选存储方案选择增量更新或受控重建，并说明行为。
- 检索和重排应能同时处理多个文档，逐条显示正确来源。PDF 使用物理页码；后续其他格式应保留适合该格式的可核查定位信息，例如章节、段落或行号，不能把 PDF 页码假定为所有格式都有。
- 新增格式时，通过实现加载器或解析适配器将其转换为统一的文档与来源信息；核心流程依赖统一接口，不针对单一文件添加条件分支。切片、索引、检索及重排组件也应允许通过接口或配置替换，避免为假定的未来格式预先引入不必要的复杂架构。
- 扩展验收：在首个测试 PDF 之外，再加入至少一份不同内容的 PDF，分别检索两份文档中的已知内容，人工核对文件、位置和原文；再次添加同一文档时验证系统的去重或更新行为。验证新增文档不需要修改核心流程。其他格式在实际引入时，增加对应的加载和来源定位验收。

## 6. 模块需求与验收

### 6.1 文档加载

**目标**：读取 PDF，获得可用于后续处理的文本和来源信息。

**输入**：PDF 路径；可选的页面范围。

**输出**：按页或可追溯至页面的文本、文件名、PDF 页码，以及加载成功、失败或空文本页面的统计。页码采用 PDF 阅读器中的物理页码，从 1 开始；如文档印刷页码不同，应明确区分。

**人可读检查**：展示指定页面的提取文本和页码，让使用者对照 PDF 原文检查中文、段落顺序和明显缺失。错误应指出文件及受影响页面。

**验收**：

1. 对测试 PDF 的固定页面范围加载成功，并能逐页显示文本及物理页码。
2. 全文加载时报告总页数、成功页数和空文本或失败页数；不能将空文本页面默认为解析成功。
3. 人工抽查首页、中间和末尾的可提取文本页面，与 PDF 对照并记录异常；缺失或乱码须可见，不能静默跳过。

### 6.2 文本切片

**目标**：将加载结果切分为适合检索的文本片段，并保留上下文和来源。

**输入**：加载后的文本及来源信息；可配置切片大小和重叠量，明确其计量单位。

**输出**：片段编号、文本、长度、来源文件和对应物理页码或页码范围。

**人可读检查**：列出指定页面的切片及相邻片段，方便检查断句、上下文和重叠；给出片段数量及长度概览。

**验收**：

1. 对固定页面范围生成非空切片，每个片段均可追溯到来源页码。
2. 人工检查至少一组相邻片段，确认切分边界和重叠情况可见，无明显不可读乱码；发现的断句或跨页问题须记录。
3. 可调整切片参数并重新运行，输出中能辨认所用参数，便于比较。

### 6.3 向量化与索引

**目标**：将切片转换为可搜索的索引，并建立索引记录与原文片段之间的关联。

**输入**：文本切片、嵌入模型配置及索引存储配置。

**输出**：可复用的索引，以及模型名称、切片数量、成功或失败数量和索引位置等信息；向量本身不作为主要阅读内容。

**人可读检查**：查看索引构建概览，并通过片段编号核对索引记录对应的原文和页码。

**构建与使用约束**：

- 随索引记录嵌入模型及版本、向量维度、切片配置、文档标识及内容版本等必要信息。加载、追加和查询时检查相关配置的兼容性；不兼容时明确拒绝，并提示重建或使用独立索引。查询须使用与索引兼容的嵌入模型。
- 明确采用增量更新或受控重建，并说明重复添加同一文档、文档内容变化和来源位置变化时的处理方式。不得静默重复添加、覆盖其他文档或指向错误来源。
- 构建失败时报告原因、已成功及失败的片段数量，并明确索引是否完整、是否可用及如何恢复；不得将部分构建的索引当作完整索引交付。
- 片段编号须在已保存索引的生命周期内可用于查回对应文本和来源；不同切片运行之间不假定编号不变。
- 使用模型或外部存储前，记录运行环境、资源及成本要求；使用外部服务时说明发送的数据和配置方式，不硬编码密钥。

**验收**：

1. 固定页面范围的非空切片可完成索引，统计中的成功与失败数量可核对；失败时给出原因。
2. 重新加载已保存的索引后，能找回对应片段的文本和来源，不必重新解析 PDF。
3. 全量处理时记录所用模型、参数及处理结果；模型或切片配置变化时，明确需要重建或隔离索引，避免混用。
4. 检查不兼容配置、重复添加、文档内容或来源位置变化及构建失败的处理，核对提示、记录和实际索引状态。

本阶段验证索引构建、持久化及来源关联；语义召回质量在检索阶段使用固定问题和人工核验评估，索引构建成功不代表检索质量达标。

### 6.4 检索

**目标**：根据自然语言问题，从索引中找出可能相关的原文片段，并确保每条结果都能回到原始文档核对。

**输入**：问题、索引及可配置的召回数量。

**输出**：按顺序排列的候选片段，包括可完整查看的原文、来源文件、PDF 物理页码或页码范围、片段编号、排名和检索分数；说明分数的含义及排序方向。页码从 1 开始，跨页片段须列出覆盖的页码范围。来源信息应来自加载和切片时保留的元数据，并随索引持久化。

**人可读检查**：输入问题后逐条阅读候选片段，直接对照 PDF 判断相关性和来源是否正确；无结果时明确提示。

**验收**：

1. 使用测试 PDF 中人工确认存在答案的至少 3 个问题运行检索，记录问题、预期来源、候选结果及人工判断。
2. 每个结果均显示完整可查看的原文、来源文件、片段编号、排名和可核对的物理页码或页码范围；人能据此打开原 PDF 并找到对应内容。结果数量遵循配置，实际不足时如实显示。
3. 重新加载索引后执行相同检查，确认来源信息仍然可用；缺少文件、页码或原文等必要来源信息的结果不得作为可溯源结果交付，须明确提示来源缺失及受影响片段。
4. 至少包含一个文档中没有明确答案的问题，记录是否召回无关片段；不能把有召回结果视为已找到答案。

### 6.4.1 可选进阶：混合检索（Hybrid Retrieval）

混合检索用于比较词法匹配和语义匹配对召回质量的影响，不替代基础的向量检索，也不改变“结果必须可追溯”的要求。本能力在基础检索阶段完成并经人工确认后实施，优先作为可配置的对照模式；重排仍是独立阶段，不能把混合检索的融合顺序当作重排结果。

**目标**：将当前的 dense 向量召回与本地词法召回结合，在包含专有名词、条款、标题或原文关键词的问题上减少召回遗漏，同时保留语义改写问题的召回能力。

**输入**：问题、已保存索引、与索引兼容的嵌入模型，以及可配置的检索模式和各路候选数量。词法检索必须使用与向量索引相同的已保存 Node 正文，不重新解析 PDF；默认不把文档或问题发送到外部服务。

**候选来源**：

- dense 分支使用现有 `VectorStoreIndex` 和相同的模型兼容性检查；
- lexical 分支在索引保存的 Node 上建立本地 BM25 或当前 LlamaIndex 版本提供的等价词法检索器；
- 两个分支都必须保留 Node ID、完整正文和文件来源元数据，来源校验规则与基础检索一致。

**融合规则**：

1. 两个分支分别取候选并保留各自排名；
2. 使用 Reciprocal Rank Fusion（RRF）或当前版本中语义等价的排名融合方法合并候选；
3. 不直接相加向量相似度和 BM25 分数，因为二者量纲和排序含义不同；
4. 融合结果展示融合排名，并在需要时同时展示 dense 排名、lexical 排名及各自分数；
5. 词法组件不可用时不得静默降级为 dense。命令应明确报错，或由调用方显式选择 `dense` 模式。

**配置边界**：检索入口提供 `dense` 和 `hybrid` 两种模式，默认保持 `dense` 以保留现有实验基线。`dense_top_k`、`lexical_top_k`、最终 `top_k` 和 RRF 参数集中配置并记录在运行日志或实验记录中；不同索引、切片参数和模型配置仍按基础检索的兼容性规则处理。

**验收**：

1. 使用与 dense 基线完全相同的固定问题、索引、模型和最终 `top_k`，至少比较 `dense` 与 `hybrid` 两组结果；不得只更换问题或候选数量后宣称效果改善。
2. 至少覆盖三个文档内有明确依据的问题和一个文档内没有明确依据的问题，其中包含一个依赖原文关键词或专有名词的问题。
3. 记录每个问题的 dense 候选、lexical 候选、融合后的排名、来源页码、人工判断和运行成本；必要时补充 Recall@K、MRR 等指标，但自动指标不能替代人工核对。
4. 检查混合检索是否仍能从持久化索引恢复完整正文和来源；来源字段缺失或不合法的 Node 不能作为可追溯结果交付。
5. 对无明确答案的问题，记录混合检索返回的候选及其相关性；不得因为融合后仍有候选就判定资料中存在答案。资料不足提示属于后续回答阶段或专门的证据判断能力。
6. 词法检索组件缺失、索引损坏或配置不兼容时，验证错误信息清晰且不会发布或返回来源不完整的结果。

**已知边界**：混合检索主要改善候选召回，不能保证首条结果上下文最纯、不能替代重排，也不能单独判断问题是否超出文档范围。若词法召回和 dense 召回均无改善，应保留实验结果，不为了排名变化而强行启用 hybrid 默认模式。

### 6.5 重排

**目标**：对检索候选片段重新排序，提高靠前结果的相关性。

**输入**：问题、检索候选片段及可配置的重排数量或模型。

**输出**：重排后的片段、来源文件、物理页码或页码范围、片段编号、原排名、新排名和重排分数，确保重排后仍可核对原文。检索分数和重排分数分别标注，不假定二者可直接比较。

**人可读检查**：并列或清晰展示重排前后的顺序，方便观察哪些片段上升或下降及其内容。

当前实现采用两阶段基线：dense 检索先取最多 20 个候选，再使用本地 CrossEncoder 重排并交付前 5 个结果（`dense top 20 → rerank top 5`）。候选数量和最终数量可配置，但最终数量不得大于候选数量；未提供本地重排模型时仍可运行 dense 基线，启用重排后模型缺失或不可用必须明确失败，不能静默降级。

**验收**：

1. 使用与检索模块相同的测试问题和候选集合，展示重排前后结果和来源。
2. 人工记录相关片段排名的变化；如未改善或变差，应如实记录，不以排名变化本身判定成功。
3. 重排不可用或失败时明确报错；若提供跳过重排的选项，输出须标明实际使用的是原始检索顺序。

### 6.6 基于来源的回答

**目标**：基于检索或重排得到的文档片段回答问题，方便读者核查依据。

**输入**：问题、选定的候选片段和生成模型配置。

**输出**：可读回答、所依据的原文片段及文件名、物理页码。来源标注应与具体陈述对应，便于核对。

**人可读检查**：阅读回答并跳转或翻阅对应 PDF 页面，判断回答是否忠于原文、是否遗漏限定条件。

当前实现先复用检索或重排结果，把片段按交付顺序编号，再交给 OpenAI 兼容的生成模型；提示词要求只依据证据回答、用 `[n]` 标注关键结论，并在证据不足时明确说明。只按排名取前 K 会把“你好”这类与文档无关的问题也塞进证据，模型随后会把无关片段总结成答案；因此回答前还要按相关度过滤：重排结果使用 rerank 分（默认不低于 0.3），dense 结果使用相似度（默认不低于 0.5），低于门槛的片段不作为证据并重新编号，全部低于门槛时直接提示资料不足，不调用模型。阈值与模型和索引相关，换模型后必须重新校准，命令行和服务启动参数都可调整。默认使用火山方舟的 `glm-5.3-flash`，问题和片段会发送到外部服务并产生费用，密钥只从环境变量读取；地址、模型和输出上限集中配置，可临时覆盖。程序会核对引用编号是否存在，并在没有引用或编号越界时提示，但不会自动判断回答是否忠于原文。没有可交付片段时不调用模型，直接提示资料不足。

**验收**：

1. 对至少 3 个文档内有明确依据的问题给出回答，并展示可核对的来源及原文片段。
2. 对至少 1 个文档无明确依据的问题，提示资料不足；不得把无关片段当作答案的依据。
3. 人工核对回答中的关键陈述与引用是否一致；对不准确或缺失的情况记录问题，不以生成成功等同于回答正确。

### 6.7 局域网接口与 iPhone 客户端

**目标**：让同一局域网内的 iPhone 通过 HTTP 调用本机已有的检索、重排和回答能力。客户端不实现 RAG，也不持有索引、嵌入模型或云端生成密钥；所有文档处理和外部模型调用仍在本机完成。

**输入**：已构建的索引、自然语言问题，以及可配置的候选数量、交付数量和是否重排；生成模型地址、模型名和密钥只来自服务端配置或环境变量。

**输出**：

- 健康检查：返回索引路径、片段数、模型身份和配置是否可加载，供客户端判断服务是否可用。
- 检索：返回按排名排列的候选片段，包含正文、文件名、物理页码、片段 ID、分数和来源状态。
- 回答：返回回答、引用检查结果和所用证据；证据包含文件名、物理页码、来源状态和完整原文。
- 流式回答：`POST /ask` 的请求体用 `stream` 参数控制返回形式。`stream` 为 `false`（默认）时返回一次性 JSON；为 `true` 时返回 Server-Sent Events，依次发送 `status`（检索中、生成中）、`evidence`（证据列表）、`delta`（生成文本增量）、`done`（完整回答、引用检查和证据）和 `error`（失败原因）。客户端在检索完成后即可展示来源，不必等整段回答生成完。两种形式使用同一套检索、引用检查和截断检查规则。
- 错误：使用明确的 HTTP 状态码和中文消息，区分参数错误、索引不可用、模型不可用和生成失败；不回显密钥、堆栈或无关的本机路径信息。

**接口约束**：

- 默认只监听 `127.0.0.1`；需要手机访问时必须显式传入 `--host 0.0.0.0`，并在启动输出中说明当前监听范围和风险。
- 支持可选的 Bearer Token：设置 `RAG_API_TOKEN` 后所有非健康检查请求都要携带；未设置时按“仅可信局域网自用”处理，并在启动输出中提示。
- 问题长度、候选数量和交付数量设有上限；超限返回 4xx，不截断后继续执行。
- 同一索引的模型兼容性、来源核验和来源状态沿用检索与回答模块的规则，接口层不复制这些判断。
- 生成失败时返回错误和已取得的证据编号，便于在手机端判断是检索还是生成环节出问题。
- 流式响应一旦开始发送，HTTP 状态码已经确定，检索或生成失败只能通过 `error` 事件报告；鉴权、参数和索引检查在开始发送前完成，仍使用对应的 4xx 状态码。
- 流式回答的文本增量为纯文本，不包含模型推理内容；截断和空回答按非流式接口的同一规则判定为失败，不把半截回答当作完整结果交付。
- 服务端只记录必要日志，不记录问题全文、片段正文或密钥。

**iPhone 客户端约束**：

- 使用 SwiftUI；只做模拟器与自签真机运行，不包含账号、同步、推送或上架所需能力。
- 设置页只填写并持久化服务器地址，地址需校验协议和主机。当前版本不接入 Token，服务端也默认不鉴权；若服务端启用了 Token，客户端把 401 转成明确提示，不提供输入框。
- 问答页是默认入口，输入问题后调用 `POST /ask` 并固定 `stream: true`：检索阶段先显示状态，收到 `evidence` 后立即渲染证据，回答随 `delta` 增量显示，`done` 后展示完整回答、引用检查、证据列表和来源状态。证据可复制，页码与文件名足以回到 PDF 核对。
- 回答按 Markdown 渲染：支持标题、段落、加粗、斜体、行内代码、链接、无序列表、有序列表、引用、分隔线和围栏代码块；其余语法按原文显示。流式输出中尚未闭合的标记允许暂时按纯文本降级，收到 `done` 后按完整文本重新渲染。
- 流式解析按 Server-Sent Events 规则处理 `event`、`data` 和空行分隔，不假设一次网络读取恰好包含完整事件；跨读取的事件由解析器缓冲。
- 流在 `done` 之前结束、收到 `error` 或网络中断时，明确标记本次回答失败或不完整，保留已展示的证据，不把半截文本当成完整回答。
- 使用 URLSession 异步请求，支持取消和超时；新提问或切换页面时取消上一请求。服务未启动、地址错误、索引不兼容、生成失败和流中断分别给出可理解的提示。
- 问答页与设置页通过底部标签切换；生成过程中仍可查看设置页，修改地址只影响后续请求。
- 明文 HTTP 仅用于局域网，需要在客户端声明本地网络权限并配置 ATS 例外；不把该配置用于公网地址。
- 客户端不缓存书籍正文或索引；是否缓存最近回答由后续需要决定。

**验收**：

1. 启动服务后，`curl` 能完成健康检查和一次文档内问题的检索；返回的来源、页码与命令行结果一致。
2. 同一局域网内的 iPhone 填入地址后，能对至少 3 个文档内有明确依据的问题得到回答，并展示可核对的证据页码。
3. 对文档内无明确依据的问题，客户端显示资料不足或低相关提示，不把无关片段当作答案。
4. 服务未启动、地址错误、Token 缺失或错误、索引不兼容时，客户端显示对应错误且不崩溃；服务端不泄露密钥。
5. 服务端未设置 Token 时启动输出明确提示仅限可信局域网；设置 Token 后，未携带或携带错误 Token 的请求被拒绝。
6. 问题超长、候选数量超限或索引目录不存在时，接口返回 4xx 和可读原因，不产生部分结果。
7. 使用 `curl -N` 调用 `/ask` 并传 `"stream": true`，能在生成结束前依次收到 `status`、`evidence` 和增量 `delta`；最终 `done` 事件中的回答、引用检查和证据与 `stream` 为 `false` 时一致。检索或生成失败时收到 `error` 事件，不出现“已发送部分回答却无说明”的情况。
8. 在模拟器或真机上输入问题，先看到检索状态和证据，再看到回答逐段出现；完成后引用检查、证据页码与命令行一致，加粗和列表按 Markdown 渲染而不是显示原始符号。生成中断开网络或停掉服务，界面显示失败，不把半截回答标记为完成。

## 7. 统一测试与结果记录

- **固定测试集**：从 PDF 中人工选取至少 3 个不同主题、文档内有明确依据的问题，记录预期物理页码和支持答案的原文；再加入至少 1 个文档无明确依据的问题。具体问题在查看原文后确定，不预设文档内容。
- **测试顺序**：先固定页面范围测试加载、切片和索引；再用全量文档建立检索用索引，运行相同问题以比较检索、重排和回答。每次记录文档版本或文件标识、页面范围、关键参数、模型和运行日期。
- **人工记录**：每次记录输入、实际输出、预期来源、人工判断、异常和待处理事项。判断可使用“符合 / 部分符合 / 不符合”，并写明依据；最终质量由人工核查，不能仅凭分数判定。
- **可读性**：结果使用清晰标题、编号和中文说明；正文保留完整可核对的片段，必要时提供摘要视图，但不得让截断后的展示成为唯一可查看内容。
- **错误与边界**：文件不存在、PDF 页面无可提取文本、索引或模型不可用、无检索结果等情况均应给出可理解的提示；不输出未经授权的密钥等敏感信息。

## 8. 交付顺序与完成标准

1. 文档加载：能查看页面文本并核对来源。
2. 文本切片：能查看相邻片段、边界和页码。
3. 向量化与索引：能构建、保存并重新加载索引。
4. 检索：能用固定问题查看候选片段及来源。
5. 重排：能比较相同候选的前后顺序。
6. 回答：能查看基于原文的回答、引用和资料不足提示。
7. 局域网接口与 iPhone 客户端：手机能通过局域网提问，并核对回答引用的来源。

每个阶段完成后，运行对应验收并保存或记录结果，提供运行方式并等待用户亲自运行和明确确认结果 OK；收到确认后才能进入下一阶段。发现问题先定位并修复，等待用户重新运行确认。最终交付应附运行说明、配置说明、实际测试记录和已知限制。任何未完成或未验证的项目均须明确标记，不能称为通过。

## 9. LlamaIndex 学习与实践

### 学习方式

优先通过 LlamaIndex 官方提供的抽象、组件和集成完成各模块，并结合实际安装版本查阅官方文档。先跑通可验证的基础路径，再按下表逐项实践、对比；具体类名、导入路径及可用集成以安装版本和官方文档为准。不要为了覆盖术语而增加与项目目标无关的复杂度，也不要假定所有能力都属于核心包或免费提供。

| 阶段 | 优先实践的技术点 | 对照实验与学习复盘 |
| --- | --- | --- |
| 文档加载 | Reader、Document、元数据及来源管理 | 比较默认加载与适配器扩展；说明加载器与文档对象的职责、如何保留来源。 |
| 切片 | Node、NodeParser / TextSplitter、切片大小与重叠、节点关系 | 用同一页面比较至少两组切片参数或两种切分策略；解释上下文完整性、检索粒度与成本的取舍。 |
| 索引 | 嵌入模型、VectorStoreIndex、向量存储、索引持久化与加载 | 解释 Document、Node、Index 和向量存储的关系；比较重建与更新的行为，并核查来源是否保留。 |
| 检索 | Retriever、相似度检索、Top-K、元数据过滤 | 使用相同问题调整 Top-K；在多文档场景按来源过滤，比较结果并解释召回与精度的取舍。 |
| 重排 | Node Postprocessor、重排模型及候选数量 | 对同一候选集合比较重排前后结果；说明检索与重排的职责、延迟和成本。 |
| 回答 | Query Engine、Response Synthesizer、来源节点及引用 | 比较只检索与生成回答的输出；解释如何提供证据、如何处理证据不足以及幻觉风险。 |
| 评估与观测 | 库支持的评估、回调或可观测能力 | 结合固定测试集记录检索与回答结果、耗时及可获得的成本信息；区分自动评估与人工核查，并说明其局限。 |
| 扩展 | 自定义 Reader、转换组件或 Retriever 的接口 | 结合实际需要实现至少一个小型扩展，解释扩展边界与开闭原则，并验证原有流程仍可运行。 |

### 建议的进阶实践

基础流程与各阶段验收完成后，按需要选做混合检索、查询改写或分解、不同索引策略、摄取流水线及缓存等能力。混合检索优先按 6.4.1 的 dense 基线对照流程实施，再决定是否保留为默认模式。每项先确认当前版本和可用集成，再说明它解决的问题、额外依赖及成本，用相同测试问题对比效果；结果不佳也应保留记录。进阶能力不替代基础流程和溯源要求。

### 学习产出与验收

1. 每个已实现模块记录使用的 LlamaIndex 组件、职责、输入输出、关键配置及其与上下游的关系，附可复现的运行方式。
2. 至少完成切片、检索和重排各一组对照实验，记录问题、配置、结果、来源和人工判断，说明适用场景及取舍；有失败或无改善时如实记录。
3. 整理供学习复盘的问题与回答，覆盖完整 RAG 链路、来源追踪、核心对象、常见问题、实验结果及设计取舍；回答以项目实际实现和证据为准，不将未实现能力描述为经验。
4. 记录依赖版本、模型与集成配置、运行成本及已知限制；涉及外部服务时明确数据流向。学习记录应便于人阅读，不要求暴露密钥。
